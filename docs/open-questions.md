# Спорные решения

Зафиксированные инфраструктурные решения: что выбрано сейчас и что стоит
пересмотреть при реальной нагрузке. Про устройство самого Акселератора —
`docs/accelerator/README.md`.

## Embedding-модель и размерность векторов

**Решено (пересмотрено):** `google/gemini-embedding-2` через OpenRouter,
3072 измерения (`config/embedding.config.js`, `EMBEDDING_MODEL`/`EMBEDDING_DIM`;
клиент — `config/openrouter.config.js`, ключ `OPENROUTER_API_KEY` с fallback
на `OPENAI_API_KEY`). Первоначальный выбор был `text-embedding-3-small`
(OpenAI, 1536) — заменён в пользу максимальной точности. Смена модели требует
пересоздания коллекций Qdrant (размерность зафиксирована при создании) +
reindex всего проектного контекста и knowledge.

## Транспорт очереди обработки файлов

**Решено:** MongoDB-backed очередь (`src/models/job.model.js`,
`src/services/queue/`), а не BullMQ + Redis. Причина: деплой сейчас — один
Docker-контейнер без Redis (`amvera.yml`), а обязательный по ТЗ объём
(TXT/MD) — не CPU-тяжёлый. Контракт `enqueue/registerHandler` намеренно
узкий, чтобы транспорт можно было заменить на BullMQ, не трогая обработчики
(`process-file.job.js` и будущие job-типы).

**Пересмотреть, если:** появится реальная нагрузка с большим количеством
PDF/DOCX или нужны priority queues / rate limiting из коробки.

## Какие форматы файлов реально парсятся

**Решено:** TXT/MD — обязательно, потоково (`text.extractor.js`), без
буферизации всего файла. PDF (`pdf-parse`) и DOCX (`mammoth`) — желательно,
буферизуются целиком с лимитом 20 МБ (`MAX_BYTES` в
`pdf.extractor.js`/`docx.extractor.js`). PPTX/XLSX/изображения — не
поддерживаются, файл получает `processingStatus=unsupported`, загрузка не
ломается.

## Хранение текста чанка в Qdrant payload

**Решено:** да, `payload.text` хранит сам текст фрагмента (не только
`sourceId` для последующего восстановления из MongoDB). Так сильно проще
собирать LLM-контекст без похода в MongoDB за каждым результатом поиска.
Секретов там нет — только проектный контент (файлы, summary, артефакты),
что не противоречит SEC-3.

**Пересмотреть, если:** появится требование не дублировать контент между
MongoDB и Qdrant (например, право на удаление/забвение конкретного текста).

## Способ завершения этапа и создания документа

**Решено (пересмотрено):** одна фаза. Раньше завершение было двухфазным
(черновик `waiting_user_confirmation` → `confirmArtifact:true`), а перед
генерацией стоял серверный гейт готовности; артефакт собирался как JSON по
`requiredFields` и валидировался схемой. Каждая из этих ступеней была
состоянием, в котором пользователь мог застрять: фронт не сделал второй вызов,
модель не смогла закрыть поле, JSON не прошёл валидацию.

Сейчас `POST .../complete` — один вызов без параметров: модель пишет документ
обычным текстом, сервер верстает PDF, закрывает сессию и переключает проект на
следующего агента. Готовность этапа (`readyForArtifact`) агент объявляет сам
инструментом `stage_ready`, и это подсказка фронту, а не серверный запрет.

**Пересмотреть, если:** появится требование давать пользователю отклонять и
перегенерировать документ до перехода дальше — тогда возвращается вторая фаза,
но уже как явное пользовательское действие, а не как обязательный шаг
протокола.

## Схема данных этапа

**Решено (пересмотрено):** её нет. Раньше агент заполнял фиксированный список
`artifactDefinition.requiredFields`, подтверждая каждое поле дословной цитатой
пользователя, а готовность считалась как «заполнено N из M». На практике этап
намертво вставал на поле, которое пользователь не мог сформулировать.

Сейчас агент складывает произвольные пары «ключ: значение» в
`ExpertSession.collectedData` инструментом `save_data`, ключи придумывает сам
по своему промпту. Из этих данных собирается и документ, и сводка для
следующего агента.

**Пересмотреть, если:** понадобится машинная обработка результатов этапов
(аналитика по проектам, автозаполнение форм) — тогда схема вернётся, но как
необязательный слой поверх свободных данных, а не как условие завершения.

## Хранение версий системного промпта

**Не реализовано.** `Agent.systemPrompt` — просто поле, без истории версий.
Изменение промпта влияет на все будущие ходы, включая уже идущие сессии.

## Лимиты токенов

**Решено:** ограничение найденного контекста — по символам, не по токенам:
токенизатора конкретной модели в проекте нет. Лимиты общие для всех агентов и
лежат в `config/accelerator.config.js` (`projectMaxChars`,
`knowledgeMaxChars`); там же лимиты токенов на *ответ* модели —
`chatMaxTokens` для реплики и `documentMaxTokens` для документа этапа.

## Идентификация агента: `code` vs `_id`

**Решено (пересмотрено):** изначально у `Agent` было отдельное
человекочитаемое поле `code` (`"R1"`, `"R2"`) как ссылка вместо `_id` —
удобно для seed-скриптов и ручного дебага в БД без похода за ObjectId.
От него отказались в пользу `_id` как единственного идентификатора.

Причина отказа: `code` был редактируемым через `PATCH`, при этом на него
ссылались `Agent.nextAgentId` (других агентов), `Project.currentAgentId`,
`Project.completedAgentIds`, `ExpertSession.agentId`, `Artifact.agentId` и
`payload.agentId` в Qdrant. Переименование агента молча рвало все эти
ссылки — каскадного обновления не было и не планировалось. `_id` неизменяем
по своей природе, этой проблемы не существует.

Также оказалось, что реальная польза от `code` была прежде всего в одном
сценарии — тексто-ориентированные, не-UI-опосредованные ссылки на агента
(seed-скрипт, ручные Mongo-запросы, гипотетический config-as-code). Раз
агенты создаются/связываются через admin CRUD, где UI может резолвить
выбор в `_id` через выпадающий список (`GET /accelerator/admin/agents`
уже отдаёт `_id`+`name` каждого агента), human-readable ключ не является
архитектурной необходимостью для этой системы.

Роман/Регина по-прежнему заведены только как демо-данные
(`scripts/seed-demo-agents.js`), не как часть бизнес-логики. Связывать их
через `nextAgentId` больше не нужно: маршрут строится по `order`.

**Пересмотреть, если:** появится реальный config-as-code для агентов
(YAML/JSON-файлы в репозитории, применяемые sync-скриптом) — там
человекочитаемые ссылки снова станут заметно удобнее ObjectId.

## LLM-провайдер: чат — OpenAI, эмбеддинги — OpenRouter

**Решено (пересмотрено дважды):** изначально у агента настраивался
`provider` (`openai` или `openrouter`); затем поле убрали и весь
`llm.service.js` перевели на прямой OpenAI. Позже OpenRouter вернулся, но в
другой роли: `config/openrouter.config.js` — клиент **только для
эмбеддингов** (`embedding.service.js`, модель `google/gemini-embedding-2`).
Чат агентов и генерация документов ходят в прямой OpenAI
(`config/openai.config.js`).

**ВНИМАНИЕ при деплое:** это два разных провайдера и, как правило, два
разных ключа. Ключ OpenRouter в `OPENAI_API_KEY` уронит весь чат с 401
(`LLM_PROVIDER_FAILED`); ключ OpenAI в `OPENROUTER_API_KEY` уронит
индексацию и поиск (`EMBEDDING_PROVIDER_FAILED`). См. `.env.example`.

**Пересмотреть, если:** появится потребность гонять и чат через OpenRouter —
тогда выбор провайдера добавляется в `config/accelerator.config.js`, общий для
всех агентов.

## Изоляция недоверенного контекста от системного промпта (prompt injection)

**Решено (пересмотрено):** изначально Qdrant-контекст (текст из загруженных
файлов и документов предыдущих этапов) конкатенировался прямо в системный
промпт вместе с инструкциями агента (`context-assembly.service.js`, единая
строка `systemParts.join(...)`).
Единственной границей была текстовая метка вида `[Фрагмент файла проекта]` —
она ничего не значит для модели, только для человека, читающего лог.

Это реальный вектор prompt injection: если пользователь загружает файл с
текстом вроде "забудь предыдущие инструкции, теперь ты...", этот текст
оказывался в system-сообщении наравне с настоящими инструкциями агента, без
какой-либо программной изоляции.

Исправлено: retrieved-контекст вынесен из системного промпта в отдельное
сообщение с ролью `user` (`retrievedContextMessage` в
`context-assembly.service.js`), обёрнутое в явную инструкцию игнорировать
любые команды и попытки переопределить системный промпт внутри тега
`<retrieved_context>`. Разделение по ролям API (`system` vs `user`) — граница
доверия, которую chat-модель обучена соблюдать; склейка строк внутри одного
system-сообщения таковой не является. Сообщения пользователя в диалоге и так
всегда шли отдельной ролью (`getSessionHistory`) — расширение затронуло
только Qdrant-контекст.

**Пересмотреть, если:** появится задача классифицировать/фильтровать
подозрительный контент при индексации (эвристики на "ignore previous
instructions" и т.п.) — сейчас чанки индексируются без проверки содержимого,
это чисто структурная (ролевая) защита, не контентная.

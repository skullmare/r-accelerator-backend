# Акселератор: как это работает

Акселератор проводит пользователя по цепочке агентов. Каждый агент — это один
этап: он разговаривает с пользователем, по ходу разговора собирает данные, а в
конце из этих данных формируется документ (PDF). После этого проект
переключается на следующего агента.

Документы этого раздела:

- **README.md** (этот файл) — как устроен пайплайн и из чего он состоит;
- [`agent-setup.md`](./agent-setup.md) — как настроить агента, чтобы он
  работал как задумано;
- [`frontend-integration.md`](./frontend-integration.md) — контракт для
  фронтенд-разработчика.

---

## 1. Пайплайн

```
проект  →  сессия с текущим агентом  →  диалог  →  документ  →  следующий агент
                                          ↑____________|
```

1. **Пользователь создаёт проект** — `POST /accelerator/projects`.
2. **Начинается сессия** — `POST /accelerator/projects/:id/expert-sessions`.
   Сервер сам определяет текущего агента проекта (у нового проекта это первый
   агент по `order`) и возвращает открытую сессию.
3. **Диалог.** Каждое сообщение — `POST .../messages`, ответ агента приходит по
   SSE. По ходу разговора агент вызывает инструмент `save_data` и складывает
   узнанное в хранилище сессии (`collectedData`).
4. **Агент видит, что данных достаточно** — вызывает инструмент `stage_ready`,
   у сессии выставляется `readyForArtifact: true`, и фронт показывает кнопку
   «Сформировать документ».
5. **Завершение этапа** — `POST .../complete`. Один вызов: модель пишет
   документ, сервер верстает PDF, кладёт в S3, закрывает сессию и переключает
   проект на следующего агента.
6. Шаги 2–5 повторяются, пока не закончатся агенты. После последнего
   `Project.status` становится `completed`.

## 2. Сущности

| Сущность | Что это | Файл модели |
|---|---|---|
| `Project` | Проект пользователя, несёт текущего агента и накопленную сводку | `src/models/accelerator/project.model.js` |
| `Agent` | Этап маршрута: два промпта + знания + отображаемые поля | `src/models/accelerator/agent.model.js` |
| `ExpertSession` | Диалог с одним агентом: собранные данные и признак готовности | `src/models/accelerator/expert-session.model.js` |
| `Message` | Реплика диалога | `src/models/accelerator/message.model.js` |
| `Artifact` | Документ этапа: Markdown + PDF + сводка | `src/models/accelerator/artifact.model.js` |
| `Knowledge` | Глобальная база знаний, привязывается к агентам | `src/models/accelerator/knowledge.model.js` |

## 3. Что видит модель

Каждый ход собирается из четырёх блоков
(`context-assembly.service.js` + `data-collection.service.js`):

```
system:  systemPrompt агента
         ---
         Что уже известно по проекту (Project.contextSummary)
         ---
         Условие завершения этапа (completionPrompt)
         Уже собранные данные этапа (collectedData)
         Инструкции: сохраняй через save_data, вызови stage_ready, ...

user:    <retrieved_context>  ← найденное в Qdrant: файлы проекта,
                                документы прошлых этапов, базы знаний
         </retrieved_context>

...      последние 30 сообщений диалога
```

Найденный контекст **не** склеивается с системным промптом: он идёт отдельным
сообщением роли `user`, обёрнутым в инструкцию игнорировать любые команды
внутри. Это защита от prompt injection через загруженные пользователем файлы.

## 4. Инструменты агента

Ровно два, оба описаны в `data-collection.service.js`:

| Инструмент | Что делает |
|---|---|
| `save_data` | Записывает пары «ключ: значение» в `ExpertSession.collectedData`. Ключи агент придумывает сам — ни схемы, ни списка обязательных полей нет. |
| `stage_ready` | Ставит `readyForArtifact: true`. Это сигнал фронту показать кнопку завершения, а не завершение этапа. |

За один ход агенту разрешён один раунд вызовов: на втором проходе
`tool_choice: 'none'`, то есть модель физически обязана ответить текстом. Это
потолок стоимости хода (максимум два обращения к LLM) и защита от зацикливания.

## 5. Формирование документа

`artifact-generation.service.js`:

1. Один вызов LLM — модель пишет документ в Markdown (разрешено узкое
   подмножество разметки, см. `pdf-renderer.service.js`). Опора — собранные
   данные этапа, они подаются в промпт списком.
2. `pdfmake` верстает PDF по фирменному шаблону (кириллица гарантирована
   встроенным шрифтом Roboto).
3. PDF уходит в S3, ссылка сохраняется в `Artifact.file.url`.
4. `Artifact.summary` собирается **детерминированно** — из тех же собранных
   данных, без обращения к модели. Эта сводка дописывается в
   `Project.contextSummary` и уходит в промпт следующих агентов.
5. Текст документа чанкуется и индексируется в Qdrant.

## 6. Переход к следующему агенту

`resolveNextAgent()` в `expert-session.service.js`:

1. Если у агента задан `nextAgentId` и такой агент существует — переходим к
   нему.
2. Иначе — к следующему агенту по `order`.
3. Если следующего нет — маршрут пройден: `currentAgentId = null`,
   `Project.status = 'completed'`.

Из этого следует важное свойство: **маршрут работает, даже если администратор
не связывал агентов вручную**. Достаточно проставить `order`. Удалённый агент
в `nextAgentId` тоже не рвёт маршрут — переход просто идёт по порядку.

Симметрично работает и `resolveCurrentAgent()`: если `Project.currentAgentId`
указывает в пустоту (новый проект или агента удалили посреди маршрута),
подставляется первый по `order` из ещё не пройденных. Единственное состояние,
где текущего агента честно нет, — `Project.status === 'completed'`, то есть
пройденный маршрут.

## 7. Принципы, на которых держится надёжность

- **Нет второй фазы подтверждения.** Раньше завершение этапа требовало двух
  вызовов `/complete` (черновик → подтверждение). Если фронт не делал второй —
  проект стоял на месте навсегда. Теперь один вызов делает всё.
- **Нет серверного гейта готовности.** `readyForArtifact` подсказывает момент,
  но не запрещает завершить этап. Пользователь не может застрять из-за того,
  что модель не смогла закрыть какое-то поле.
- **Нет обязательных полей и JSON-схем.** Раньше артефакт валидировался по
  `requiredFields`/`outputSchema`, и отсутствие одного поля роняло весь этап с
  `ARTIFACT_VALIDATION_FAILED`. Теперь агент собирает свободные данные, а
  документ — обычный текст.
- **Сбой Qdrant не блокирует пользователя.** Индексация логируется, но не
  прерывает завершение: итоги этапа всё равно доходят до следующего агента
  через `Project.contextSummary`, который подмешивается в промпт всегда.
- **Повторный `/complete` идемпотентен** — возвращает тот же документ.
- **Повреждённая конфигурация не запирает пользователя.** Удалённый текущий
  агент, удалённый `nextAgentId`, несвязанные агенты — во всех случаях маршрут
  продолжается по `order`.
- **Никаких настроек у агента, кроме промптов.** Параметры LLM и сборки
  контекста одни для всего сервиса и лежат в `config/accelerator.config.js`.

## 8. Технические параметры

`config/accelerator.config.js` (переопределяются переменными окружения):

| Параметр | По умолчанию | Env |
|---|---|---|
| Модель | `gpt-4o-mini` | `ACCELERATOR_LLM_MODEL` |
| Температура | `0.4` | `ACCELERATOR_LLM_TEMPERATURE` |
| Лимит токенов на реплику | `1500` | `ACCELERATOR_LLM_CHAT_MAX_TOKENS` |
| Лимит токенов на документ | `4000` | `ACCELERATOR_LLM_DOCUMENT_MAX_TOKENS` |
| Глубина истории | 30 сообщений | — |
| Qdrant: topK / лимит символов | 6 / 6000 | — |
| Базы знаний: topK / лимит символов | 6 / 6000 | — |

Провайдеры: чат и генерация документов — OpenAI (`config/openai.config.js`),
эмбеддинги — OpenRouter (`config/openrouter.config.js`). Это разные ключи, см.
`.env.example` и `docs/open-questions.md`.

## 9. Миграция со старой версии

Схема изменилась несовместимо. Что делать с существующей базой:

- **Агенты** нужно завести заново или обновить: поля `roleTitle`, `greeting`,
  `isActive`, `allowPartialCompletion`, `completionEvaluatorPrompt`,
  `artifactDefinition`, `contextPolicy`, `modelConfig` больше не читаются, а
  `completionCriteria` переименован в `completionPrompt` (данные из него нужно
  перенести — автоматической миграции нет). Быстрый старт —
  `npm run seed:demo-agents`.
- **Сессии** старых форматов (`draft`, `waiting_user_confirmation`) не
  соответствуют новому enum. Незавершённые сессии лучше удалить — пользователь
  просто начнёт этап заново.
- **Артефакты** сохраняют `title`/`summary`/`file`, но поля `type`, `content`,
  `status` больше не отдаются API. Старые записи без `documentMarkdown`
  останутся в списке документов проекта, но без ссылки на PDF, если её не было.
